# 주가예보 (Stock_Forecast)

종목 하나를 검색하면 **"지금 이 종목은 매수 구간인가 매도 구간인가"** 를 기술적 지표 +
매크로 지표를 합산한 단일 점수(-100~+100)로 보여주는 개인용 웹서비스.

- 회원가입 없이 바로 사용. 즐겨찾기·내 정보에 들어갈 때만 휴대폰 번호 입력(비밀번호·문자 인증 없음, 처음이면 자동 생성). 즐겨찾기는 `user_favorites` 에 번호(계정)별로 저장.
- 데이터 소스: **한국투자증권 KIS API** · 저장소: **Supabase(PostgreSQL)** · 갱신: 일 1회 배치
  (평일은 증분 수집, 토요일은 전량 재적재 — 아래 "수집 모드" 참고)
- 색상 규약: **상승 = 레드 / 하락 = 블루** (국내 관례)

```
Stock_Forecast/
├─ web/     Next.js 16 (App Router, TS) — 읽기 경로. Supabase에서 SELECT만.
├─ batch/   Python — 쓰기 경로. KIS 수집 → 지표 계산 → 스코어링 → Supabase 업서트.
├─ db/      schema.sql · seed_symbols.sql
└─ 시그널데스크_기획서.md · 시그널데스크_스토리보드.html
```

핵심 아키텍처는 **읽기/쓰기 분리**입니다. 사용자가 검색할 때 계산하지 않고, 매일 배치가
채워둔 테이블에서 행 하나를 읽습니다. (기획서 §7.2)

## 준비 (한 번만)

### 1. Supabase 프로젝트 + 스키마
1. [supabase.com](https://supabase.com) 에서 프로젝트 생성.
2. **SQL Editor** 에서 `db/schema.sql` 전체를 붙여넣고 실행.
3. 이어서 `db/seed_symbols.sql` 실행 (시작 유니버스 ~39종목 적재).
4. `db/schema_*.sql` 을 파일별로 실행 (기능 추가분 — 용량 추적 `schema_db_usage.sql` 포함).
   한 번에 다 붙이지 말고 **파일 하나씩** 실행하세요. `VACUUM` 같은 문장을 섞으면
   SQL Editor 가 전체를 한 트랜잭션으로 묶어 앞의 DDL 까지 롤백합니다.
5. **Project Settings → API** 에서 아래 값을 확인:
   - `Project URL` → `SUPABASE_URL`
   - `service_role` secret → `SUPABASE_SERVICE_ROLE_KEY` (서버/배치 전용, 노출 금지)

### 2. KIS API 키
1. [한국투자증권 API 포털](https://apiportal.koreainvestment.com) 에서 앱 등록.
2. `APP KEY` / `APP SECRET` 발급 → 배치 `.env` 에 입력.
3. 해외주식 시세를 쓰려면 해외 시세 이용 신청이 필요할 수 있습니다. **확인이 필요합니다.**

## 배치 실행 (쓰기 경로)

```bash
cd batch
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env      # 값 채우기 (KIS 키 + Supabase)
.venv/bin/python run.py            # 전체 종목(증분)
.venv/bin/python run.py --full     # 전체 종목(전량 재적재)
.venv/bin/python run.py 005930 AAPL  # 특정 종목만
```

- `daily_prices` / `daily_indicators` / `daily_signals` / `daily_macro` 가 채워집니다.
- 종목 단위로 재시도하며, 한 종목 실패가 전체를 막지 않습니다.
- `LOOKBACK_TRADING_DAYS` (현재 **400**) 는 전량 재적재가 받아오는 거래일 수입니다.
  평일 증분은 재검증 윈도우만 받으므로 이 값과 무관하게 종목당 1회입니다.

  | 값 | 토요일 전량 호출 | 소요 | DB 크기 |
  |---|---|---|---|
  | **400 (현재)** | **약 4,300회** | **약 40분(추정)** | **241MB 실측 (2026-10-26, 974종목)** |
  | 1000 | 약 10,700회(추정) | 약 100분(추정) | 미측정 — 무료 한도 초과 위험 |

  > 호출 수는 "국내 5회 / 해외 4회 × 종목 수"(400일 기준)로 계산한 값입니다.
  > 소요 시간과 1000일 행은 400일 실측치를 비례 환산한 **추정**이므로 확인이 필요합니다.

  > ⚠️ Supabase 무료 플랜 DB 한도가 **500MB**이고 현재 **241MB(48%)** 입니다.
  > `daily_indicators` 는 `INDICATOR_KEEP_DAYS`(400) 로 잘라 보관하지만,
  > `daily_prices` 는 과거에 받아둔 1000일치가 그대로 남아 있고(가장 오래된 행 2021-02)
  > `daily_signals` 가 매 거래일 **974행**씩 계속 쌓입니다.

  > **중복 인덱스 정리 완료 (2026-10-26, 303MB → 241MB)** — `idx_prices_ticker_date` ·
  > `idx_ind_ticker_date` · `idx_signals_latest` 를 제거했습니다. 세 테이블 모두 PK 가
  > `(ticker, trade_date)` 로 같은 컬럼을 커버하고, 웹(`web/lib/db.ts`)과 `mv_home_stats` 의
  > 조회가 전부 `WHERE ticker = ? ORDER BY trade_date DESC`(다중 티커 IN 조회 없음)라
  > PK 역방향 스캔으로 대체됩니다. 제거 후 `Index Scan Backward using *_pkey` 로
  > 비용 변화 없이 동작하는 것을 확인했습니다.
  > **같은 컬럼의 DESC 인덱스를 다시 만들지 마세요** — PK 와 중복됩니다.

  > 용량이 더 필요하면: ① `VACUUM FULL daily_indicators` · `daily_prices` (죽은 행 약 5만,
  > 8~10MB — 배타 락이 걸리므로 배치가 안 도는 시간에), ② `daily_prices` 도 보관 일수
  > 상한 적용, ③ `daily_signals` 오래된 행 정리.

### DB 용량 추적 (주 1회, 자동)

한도에 **언제** 닿는지는 한 번 재서는 알 수 없어 시계열을 남깁니다. 토요일 전량 배치가
끝날 때(지표 정리·홈 요약까지 반영된 최종 상태) `db_usage` 에 한 줄 기록하고, 쌓인
기록으로 주당 증가량과 도달 예상일을 계산합니다. 주당 1행이라 추적 자체는 1KB 수준입니다.

```bash
.venv/bin/python db_usage.py            # 측정·기록 + 추세 보고 (전량 배치가 자동 호출)
.venv/bin/python db_usage.py --report    # 기록하지 않고 쌓인 기록만 보고
.venv/bin/python db_usage.py --limit 500 # 한도(MB) 지정 — 유료 전환 시 변경
```

출력 예:

```
DB 용량: 257.0MB / 500.0MB (51%) — 2026-11-09 기준
  본문 182.0MB · 인덱스 75.0MB · 활성종목 974개
  추세: 주당 +8.0MB (측정 3회, 마지막 정리 이후만)
  한도 도달 예상: 2027-06-09 (약 30주 뒤)
```

- **마지막으로 용량이 줄어든 측정 이후만** 추세에 씁니다. 인덱스 정리나 행 삭제로 한 번
  꺾이면(2026-10-26 303MB → 241MB) 그 전까지 묶어 재면 기울기가 음수가 되어 "한도에
  영원히 안 닿는다"는 잘못된 답이 나옵니다. 20MB 이상 감소를 정리 지점으로 봅니다.
- `index_bytes` 를 따로 기록하는 이유: 중복 인덱스가 다시 생기면 본문보다 인덱스가 먼저
  불어나므로 거기서 티어납니다.
- 측정이 2회 미만이면 추세 없이 현재 용량만 보고합니다. 배치 실패로 한 주 빠져도
  날짜 간격으로 계산하므로 문제없습니다.
- 추세 계산 로직은 `batch/test_db_usage.py` 로 검증합니다 (`python -m unittest test_db_usage`).

### 수집 모드 (하이브리드)

| | 증분 (기본) | 전량 (`--full`) |
|---|---|---|
| 언제 | 평일 18:30 | 토요일 09:00 |
| KIS에서 받는 구간 | 최근 `REVISION_ROWS`(3) 거래일 이후 | 400거래일 전부 |
| 지표 워밍업 | `daily_prices`에서 `WARMUP_ROWS`(270)행 읽어 이어붙임 | 받아온 구간 그대로 |
| **종목당 KIS 호출** | **1회** | 국내 5회 / 해외 4회 |
| 하루 총 호출(974종목) | 약 976회 | 약 4,300회 |

증분은 매번 **최근 3거래일을 다시 받아 덮어씁니다.** 전량 재조회가 갖고 있던
"지난 며칠 값은 다음 실행이 알아서 고친다"는 자가치유 성질을 유지하기 위한 장치로,
거래량 정정 같은 뒤늦은 변경이 그대로 굳는 것을 막습니다.
수정주가(액면분할·유상증자) 소급 반영과 장기 누락 복구는 토요일 전량 재적재가 담당합니다.

DB에 이력이 없는 신규 편입 종목은 증분 모드에서도 자동으로 전량 수집합니다.

> **해외 미완성 행 차단**: KIS는 미국장 개장 전에도 그날 날짜의 행을 프리마켓 체결분만
> 담아 내려줍니다(예: NVDA 2026-09-04 거래량 41만 vs 정규장 1.35억). 전량 재조회 시절에는
> 다음 날 덮어써져 자연히 고쳐졌지만 증분에서는 굳어버리므로, 정규장 종료 전(D+1 06:00 KST
> 이전) 행은 저장하지 않습니다. `SKIP_INCOMPLETE_OVERSEAS=0` 으로 끌 수 있습니다.

### 매일 자동 실행 (launchd, 설치됨)
macOS LaunchAgent 2개가 설치되어 있습니다.

| Label | 시각 | 하는 일 | 종목 |
|---|---|---|---|
| `com.signaldesk.batch.us` | 평일 07:00 | 해외 증분 | 575 (주식 535 + ETF 40) |
| `com.signaldesk.batch` | 평일 18:30 | 국내 증분 | 399 (주식 359 + ETF 40) |
| `com.signaldesk.batch.full` | 토요일 09:00 | 전량 재적재 | 974 |

> launchd Label 은 서비스명을 바꾸기 전에 등록한 것이라 `com.signaldesk.*` 그대로입니다
> (이미 설치된 LaunchAgent 식별자이므로 바꾸려면 재등록이 필요합니다).

각 시장을 **그 시장이 닫힌 직후에만** 받습니다. 전 종목을 두 번 도는 게 아니라
나눠서 한 번씩이므로, 하루 총 호출은 1회 배치 때와 같은 **673회**입니다.
미국 시세 반영 지연은 13.5시간 → 2시간으로 줄어듭니다.

- 07:00인 이유: 미국장 마감이 서머타임 05:00 / 해제기 06:00 KST → 07:00이면 항상 확정 이후.
- 토요일 09:00인 이유: 금요일 미국장 종가가 토 05~06시 KST에 확정되므로 그 이후여야 안전합니다.
  (그래서 해외 에이전트에는 토요일을 넣지 않았습니다 — 전량 재적재와 중복)
- 정의: `batch/com.signaldesk.batch{,.us,.full}.plist` → `~/Library/LaunchAgents/` 에 복사됨
- 래퍼: `batch/run_daily.sh` (로그: `batch/logs/batch-{incr-kr,incr-us,full}-YYYYMMDD.log`, 30일 후 삭제)

```bash
launchctl list | grep signaldesk                              # 등록 확인
launchctl kickstart gui/$(id -u)/com.signaldesk.batch.us      # 해외 즉시 실행
launchctl kickstart gui/$(id -u)/com.signaldesk.batch         # 국내 즉시 실행
launchctl kickstart gui/$(id -u)/com.signaldesk.batch.full    # 전량 즉시 실행
launchctl bootout   gui/$(id -u)/com.signaldesk.batch.us      # 해제(중단)
```
> Mac이 켜져 있어야 실행됩니다. 24/7 실행이 필요하면 GitHub Actions cron으로 이전 가능.

## 실시간 현재가

판정 점수는 **확정 일봉 기준을 그대로 유지**하고, 화면 상단의 현재가만 장중에 실시간으로
얹습니다. `daily_prices` 에는 절대 장중 값을 쓰지 않습니다 — 미완성 봉이 섞이면
MA·볼린저·RSI가 전부 오염되기 때문입니다.

```
브라우저 → /api/stock/[ticker]/quote → live_quotes(60초 캐시) → 없으면 KIS 현재가
                                     → 장 마감이면 아예 호출 안 함 → 확정 종가 표시
```

- **테이블**: `db/schema_live_quotes.sql` 을 Supabase SQL Editor에서 실행하세요.
  `live_quotes`(현재가 캐시) + `kis_token`(토큰 공유)이 생깁니다.
- **토큰**: 웹은 발급하지 않습니다. KIS는 재발급에 분당 제한이 있고 서버리스는
  콜드스타트마다 캐시가 날아가기 때문입니다. 배치가 하루 한 번 발급해 `kis_token` 에
  넣어두고 웹은 읽어 씁니다. 잔여 유효시간이 `TOKEN_MIN_REMAINING_HOURS`(기본 12h)
  미만이면 미리 갱신합니다 — 만료 직전까지 쓰면 국내장 도중에 만료돼 실시간 현재가가
  다음 배치까지 종가로 폴백하기 때문입니다. 해외 배치(07:00)가 매일 갱신하는 셈입니다.
  테이블을 막 만든 직후라면:
  ```bash
  cd batch && .venv/bin/python kis_client.py --publish-token
  ```
- **호출량**: 종목당 60초에 1회가 상한(`QUOTE_TTL_SECONDS`). 장 마감 중에는 0회.
  실제로는 보고 있는 종목만 조회되므로 하루 수십 회 수준입니다.
- **휴장일**: 장 시간 판정은 시계만 보므로 공휴일(예: 미국 Labor Day)도 개장으로 봅니다.
  그런 날 KIS는 현재가로 직전 세션 종가를 그대로 돌려주는데, 이를 실시간이라 표시하면
  오해를 부릅니다. 그래서 **현재가가 DB의 마지막 확정 종가와 같으면 거래가 없는 것으로
  보고** 종가 표시로 넘깁니다. 공휴일 표를 관리할 필요가 없고 국내·해외 모두에 통합니다.
- **폴백**: 토큰 없음·조회 실패·타임아웃·장 마감·휴장 → 전부 조용히 확정 종가를 보여줍니다.
- **진단**: 실시간이 안 뜰 때 `/api/stock/<ticker>/quote` 를 직접 열면 `reason` 이 원인을
  알려줍니다 — `market_closed`(정상) · `no_trading`(휴장) · `kis_not_configured`(KIS 키 없음) ·
  `no_token`(kis_token 못 읽음) · `kis_failed`(KIS 호출 실패) · `supabase_missing`.
- **웹은 서비스 롤 키가 필요합니다.** `kis_token` 은 RLS 정책을 두지 않아 anon/publishable
  키로는 읽히지 않습니다(토큰이 공개되면 안 되므로 의도된 설계). 배포 환경에
  `SUPABASE_SERVICE_ROLE_KEY` 가 없고 anon 키만 있으면 다른 화면은 멀쩡한데
  실시간 현재가만 `no_token` 으로 조용히 꺼집니다.
  KIS 키를 넣지 않으면 이 기능만 꺼지고 나머지는 그대로 동작합니다.

## 웹 실행 (읽기 경로)

```bash
cd web
npm install
cp .env.local.example .env.local   # SUPABASE_URL + SUPABASE_SERVICE_ROLE_KEY

```

- 홈: 검색(자동완성) + 시장 요약(VIX/VKOSPI)

### 홈 화면에 추가 (PWA, 2026-10-28)

앱스토어 없이 홈 화면 아이콘으로 쓰게 하는 설정입니다. **`app/manifest.ts` 가 핵심** —
이 파일이 없으면 홈 화면에 추가해도 주소창이 그대로 있는 "북마크"가 됩니다.

| 파일 | 역할 |
|---|---|
| `app/manifest.ts` | `display: standalone` 로 주소창 제거, 앱 이름·아이콘·스플래시 색 |
| `app/apple-icon.png` | iOS 홈 화면 아이콘. **iOS 는 manifest 의 icons 를 보지 않습니다** |
| `public/icon-{192,512}.png` | 안드로이드·데스크톱용 (`purpose: any`) |
| `public/icon-maskable-512.png` | 안드로이드가 제조사 모양대로 잘라내는 용도 |
| `components/AddToHome.tsx` | 추가 방법 안내 (환경별로 다르게) |

아이콘은 `app/icon.svg` 하나에서 만듭니다. **원본을 고치면 반드시 다시 실행하세요:**

```bash
cd web && npm run icons
```

`maskable` 과 `apple` 을 따로 만드는 이유: 안드로이드는 아이콘을 원·사각·물방울로 잘라내서
바깥 여백이 필요하고(그대로 쓰면 캔들 끝이 잘림), iOS 는 스스로 둥근 모서리를 입혀서
투명·둥근 모서리가 없어야 합니다(그대로 쓰면 모서리에 검은 테두리가 생김).

#### 안내를 언제, 어떻게 보여 주나

- **하단 배너**: 하루에 한 번. 닫으면 그날은 다시 뜨지 않고 **다음 날 다시** 띄웁니다.
  "그날"은 기기 현지 날짜(`dayKey()`)라 자정에 바뀝니다 — UTC 로 하면 한국에서
  오전 9시에 날짜가 넘어가 버립니다.
- **전체 시트**: 두 번째 방문에 **딱 한 번만**(`SHEET_FROM_VISIT`). 가치를 한 번 본 뒤에
  권해야 추가율이 올라가지만, 매일 전면으로 막으면 성가시므로 그 뒤로는 배너만 남습니다.
- **이미 홈 화면 앱으로 실행 중이거나(standalone) PC 면 아예 띄우지 않습니다.**

저장하는 값은 셋뿐입니다 — `sd.a2hs.visits`(방문 수), `sd.a2hs.hiddenDay`(닫은 날),
`sd.a2hs.sheetSeen`(시트를 보여 준 적 있는지). 전부 `try/catch` 로 감싸 시크릿 모드에서
접근이 막혀도 안내는 동작합니다.

#### 홈 화면에 추가했는지 알 수 있나

| 알고 싶은 것 | iOS | 안드로이드 |
|---|---|---|
| 추가하는 **순간** | ❌ 이벤트가 없습니다 | ✅ `appinstalled` |
| 추가한 뒤 **홈 화면에서 실행**했을 때 | ✅ `navigator.standalone` | ✅ `display-mode: standalone` |
| 사파리에서 **"이미 추가했는지"** | ❌ 알 수 없습니다 | △ |

**iOS 는 추가 자체를 알려 주지 않습니다.** 알 수 있는 건 "홈 화면에서 실행됐다"는
사실뿐이고, 그것도 그 실행 안에서만 압니다. 게다가 홈 화면 앱과 사파리는 저장소가
분리될 수 있어서, **추가를 마친 사용자가 사파리로 다시 들어오면 배너를 또 볼 수 있습니다.**
하루 한 번이라 크게 거슬리지는 않지만 완전히 막을 방법은 브라우저 쪽에 없습니다.

집계가 필요하면 2차에서 서버로 올려야 합니다 — standalone 으로 실행됐을 때 한 번
기록하면 "추가해서 쓰는 사람 수"를 셀 수 있고, 로그인한 사용자는 사파리 쪽에서도
그 기록을 읽어 배너를 숨길 수 있습니다.

환경마다 추가 방법이 달라 셋으로 갈라집니다:

| 환경 | 방법 | 사용자 조작 |
|---|---|---|
| 안드로이드 크롬 | `beforeinstallprompt` 를 가로채 우리 버튼으로 | **1번** |
| iOS 사파리 | **설치 API 가 없음** → 공유 → 홈 화면에 추가 수동 안내 | 3번 |
| 카카오톡·네이버 등 인앱 | **"홈 화면에 추가" 메뉴 자체가 없음** → 기본 브라우저로 내보냄 | 우회 |

인앱 브라우저 분기가 특히 중요합니다. 카톡 공유로 들어온 사용자는 아무리 안내해도
따라올 수 없어서, 안드로이드는 `intent://` 로 크롬을 직접 열고 iOS 는 주소를 복사해 줍니다.

> **확인이 필요합니다** — iOS 는 홈 화면 앱과 사파리의 쿠키 저장소가 분리될 수 있어,
> 추가한 뒤 즐겨찾기를 보려면 전화번호를 다시 입력해야 할 수 있습니다. 안내 문구에
> 미리 적어 두었지만, 실기기에서 확인한 뒤 문구를 조정하세요.

`proxy.ts` 의 matcher 에서 `manifest.webmanifest` 와 아이콘들을 제외했습니다 —
홈 화면 앱을 띄울 때마다 불리는데 토큰 검증이 필요 없는 정적 파일입니다.

## 스코어링 (기획서 §5.1)

| 그룹 | 가중치 | 지표 |
|---|---|---|
| 추세 | **40%** | MA 배열(20/60/120), 종가 vs MA20 |
| 모멘텀 | **20%** | RSI(14), MACD, 지수 대비 상대강도(RS20) |
| 밴드 위치 | **20%** | 볼린저 %B, 밴드폭(스퀴즈), 엔벨로프 |
| 거래량 | **20%** | 거래량/20일평균, OBV 추세 |
| 시장 환경 | **방향 0%** | VIX·금리·환율 — 방향이 아니라 **확신도 감쇠**로만 작용 |

각 지표를 -2~+2로 점수화 → 항목 가중평균 → 그룹 가중합 → 확신도 감쇠 →
-100~+100 → 5단계 구간 판정.

### 매크로가 방향에서 빠진 이유 (2026-09)

`backtest.py --macro` 로 FRED 8년치를 검증한 결과, 시장공통 매크로 점수는 지수
미래수익률과 **일관되게 역방향**이었습니다(H=60 IC −0.23). 후보 지표를 바꿔봐도
기간을 쪼개면 부호·크기가 크게 흔들려 방향을 맡길 만한 것이 없었습니다.

대신 안정적으로 관측된 것은 **국면에 따른 신호 신뢰도 차이**입니다:

| VIX 국면 | 기술 점수 횡단면 IC |
|---|---|
| 저변동 (<16) | +0.014 |
| 중간 | +0.029 |
| 고변동 (≥18) | **−0.067** |

그래서 매크로는 방향을 더하지 않고 `|점수|`를 줄입니다(`STRESS_DAMP`).
같은 날짜에는 모든 종목에 같은 배수가 걸리므로 **종목 간 순위는 그대로**이고,
바뀌는 것은 판정의 확신도뿐입니다.

> ⚠️ 40/20/20/20 은 기존 34/17/17/17 과 **같은 비율**(2:1:1:1)을 합 100으로 옮긴
> 것입니다. 원래 비율은 풀링 IC라는 잘못된 지표로 튜닝된 값이므로 **재도출이
> 필요합니다.** 아래 참고.

**가중치 보정**: `batch/backtest.py` 가 적재된 일봉으로 각 시점 점수를 재현하고
H거래일 뒤 수익률과의 **날짜별 횡단면 순위상관(IC)** 으로 예측력을 측정합니다.

> 2026-09에 IC 계산을 고쳤습니다. 이전에는 모든 (종목, 날짜) 관측치를 한데 섞어
> 순위를 매겨(풀링) 시계열 변동과 횡단면 변동이 뒤섞였습니다. 표준 방식은 같은
> 날짜 안에서 종목을 줄 세운 뒤 그 상관을 평균내는 것입니다. 두 방식의 값이
> 크게 달라(H=20에서 −0.076 vs −0.022), **기존 가중치는 잘못된 지표로 튜닝된
> 값**입니다.
```bash
.venv/bin/python backtest.py        # IC + 5분위 + 가중치 제안
.venv/bin/python test_synthetic.py  # 합성 데이터 파이프라인 검증
```

> ⚠️ 현재 보정은 **상승장 표본의 in-sample** 결과라 추세 비중이 높습니다.
> 더 긴 기간·out-of-sample 재검증이 필요합니다. 원안 25/25/20/15/15 로 되돌리려면
> `batch/scoring.py` 의 `WEIGHTS` 와 `web/components/IndicatorPanel.tsx` 의 `GROUP_WEIGHT` 를 함께 수정.
